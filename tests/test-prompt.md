Wayfinder Audit Strategy

Based on your audit, step back and reconsider the planning structure as a whole before modifying individual findings.

This project is still in initial planning and has no implementation code yet. I am a single developer, and the current 20–30 planning and Wayfinder files are already difficult for me to digest. I have not read all of them.

Do not preserve the existing structure merely because it exists. Preserve important knowledge, evidence, authority, and accepted decisions, but be willing to substantially consolidate or remove files when the same intended behavior can be represented more simply.

Use the installed Wayfinder contract as the constraint. In particular, "map.md" should be the normal low-resolution entry point, and U/E/F/D children should exist only when independent preservation materially improves navigation or continuation.

Re-evaluate whether the current children actually meet that bar. An item being distinct or unresolved is not by itself enough reason for a separate file.

Consider "capacity-analysis.md" as a candidate canonical source for sizing and capacity evidence. Distinguish that evidence from any actual sizing decision that still needs project or human authority.

Critically review:

- "dependency-graph.md" and any generated or committed graph data or generators;
- duplicated dependency and frontier information;
- the Coder precedent material, including whether its useful content can be reduced or incorporated into a more appropriate artifact;
- any agent-created artifact being treated as stronger authority than its provenance supports.

Propose a simpler target structure from first principles. Optimize for one developer being able to open "map.md", understand the project and current frontier, and drill into only a small number of files when necessary.

Do not change anything yet.

Show:

- the proposed target structure and the purpose of each remaining file;
- what should be consolidated, retired, or deleted;
- what knowledge must be preserved during consolidation;
- which architecture questions genuinely need resolution now and which should be deferred until implementation provides more evidence;
- roughly how much the proposal would reduce the active planning surface.

Prefer substantial simplification where justified. Do not simplify by discarding consequential unresolved knowledge, valid evidence, or accepted decisions.
